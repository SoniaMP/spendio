# INC — Monthly income

Optional per-user reference figure that answers one question: *how much is left this month after everything I have spent?* Built from one or more **income lines** (salary, freelance, rent received…), each with a validity interval. The sum of the lines in force for a month is the denominator; the numerator is everything the user has spent that month across all sheets.

Income is **not** a transaction. It never enters `expenses`, the category breakdown, the pie/bar charts, `GET /api/summary`, the month-over-month comparison or the Excel export. No aggregate anywhere switches from gross to net. This is the boundary that keeps the feature from turning into the income tracking declared out of scope in [`00.project-overview.md`](../00.project-overview.md).

## Rules

- Income lines are **per user**, never per sheet. One person, one income reality.
- `amount > 0` on every line. Negative lines do not exist; "this month I earned less" is modeled by changing the line's validity, not by a negative amount.
- The unit is the **month** (`'YYYY-MM'`). No proration, no fortnightly or weekly figures.
- **Validity intervals, not a current value.** `start_month` is required, `end_month` is nullable (`NULL` = in force indefinitely). Editing a line never rewrites closed months.
- The line type is **derived, never stored**: `end_month IS NULL` → in-force recurring; `start_month = end_month` → single month; otherwise → closed recurring (history).
- **Lines are additive, with no precedence.** The month's figure is the plain `SUM` of every line in force. A single-month line adds to the recurring ones; it does not override them.
- Intervals of the same line never overlap, which is what makes the month-scoped panel show each line exactly once.
- The **spent** side of the indicator is `expenses.user_id = actor` across **all sheets**, owned and shared. What the actor spent, wherever they logged it. Other users' expenses on a shared sheet never consume the actor's income.
- Income lines are **private to their owner**, never visible to users the actor shares sheets with — same privacy stance as recurring expense templates and expense payments.
- **Remaining may be negative.** It means "you went past the reference", not debt.
- **No carry-over** between months. Last month's leftover does not raise this month's figure.
- **No activation setting.** With zero lines no income *figure* is ever shown, so the app reads exactly as it does today; the only trace is a discreet `+ Ingresos` button in the expenses toolbar, which has to exist or the feature would be unreachable. Cancelling every line is how you turn it off.
- **Income lines have no instances.** No payment date, no "did it arrive?", no reconciliation. See the boundary in [`00.project-overview.md`](../00.project-overview.md) § Out of scope.

<summary>

### UC-INC-01 — Monthly income indicator with remaining · DONE

</summary>

- **Status:** DONE
- **Actor:** Owner user (also when viewing a sheet shared with them, with any permission)
- **Trigger:** User opens the expenses view on any sheet.

**Main flow**
1. The expenses toolbar — same row as `MonthPicker` — renders a soft bordered box holding a plain down arrow, the remaining, and the month's income figure: `⬇ 200 € · 2.000 €`. No words: the icon labels the box and the accessible name carries the full sentence.
2. The arrow is deliberately plain: an arrow-to-line reads as a download button, and the box is not one. The actions are explicit buttons inside the box — a `+` for a new line and a pencil for the panel — rather than the box itself being clickable, which nobody would discover.
3. The remaining leads, in semibold, because it answers the user's question; the income figure trails as muted, smaller context and is the part that hides on narrow screens. The remaining never hides and is never dimmed.
4. The box is recessive through **hierarchy** — soft `bg-muted/50`, muted tokens, smaller secondary size — and never through `opacity`, which would push a number people have to read below the accessible contrast ratio. Colour is reserved for one thing: a negative remaining turns `text-destructive`. No green: the palette has no token for it, and `MonthComparisonBadge` already uses green/red for "spent less / spent more" on the same screen.
5. `spent` is everything the actor spent in the visible month **across all sheets**, not the active sheet's total. It is not shown as a figure in the box; the accessible name and the panel footer state the scope, so the box does not read as contradicting `MonthTotal`.
6. Navigating months with `MonthPicker` recomputes both figures for the newly visible month.
7. The pencil opens the income panel (UC-INC-02); the `+` opens the new-line form directly (UC-INC-03).

**Alternative flows**
- **2a. No lines in force for the visible month:** the chip collapses to a discreet `+ Ingresos` button, which is the only entry point into the feature. This deliberately relaxes the "zero lines = invisible" rule below: with no affordance at all the feature would be unreachable. What stays true is that no *figure* is shown until a line exists.
- **3a. Actor is viewing a sheet shared with them in `read`:** the chip renders normally and `+` still works. Income belongs to the actor, not to the sheet; `isReadOnly` governs only the sheet's expenses.
- **Remaining is negative:** shown with the negative color. No warning, no email, no notification — alerts are out of scope.

**Outcome**
- The actor sees the figure drop as they log expenses, which is the point of the feature. No existing aggregate changed meaning.

</details>

### UC-INC-03 — Add an income line · DONE

</summary>

- **Status:** DONE
- **Actor:** Owner user
- **Trigger:** User clicks `+` on the chip, or `+ Nueva línea` in the panel.

**Main flow**
1. Form fields: label (required), amount (`> 0`), and recurrence — *"todos los meses desde ahora"* vs *"solo este mes"*.
2. Submit persists one row with `user_id = req.userId`, `start_month = visible month`, and `end_month = NULL` (recurring) or `end_month = start_month` (single month).
3. The chip and panel refresh with the new total.

**Alternative flows**
- **1a. Extra income this month** (double pay, a one-off job): this is the intended path — a new single-month line that simply adds to the recurring ones. There is no "edit only this month" on an existing line for this case.

**Outcome**
- One row, no interval splitting. The user sees literally what the total is made of.

### UC-INC-04 — Edit an income line, asking for the change scope · DONE

</summary>

- **Status:** DONE
- **Actor:** Owner user
- **Trigger:** User clicks the pencil on a line in the panel.

**Main flow**
1. The edit dialog prefills the name and amount, and asks which months an amount change affects: **"Desde {mes} en adelante"** vs **"Solo en {mes}"**. The choice sits inline above the form, visible before submitting, matching how `ExpenseFormDialog` already asks the same kind of question for recurring expenses. The user is never asked to reason about intervals. The recurrence choice is **not** offered: an edit cannot turn a recurring line into a single-month one.
2. `IncomeChangeScope.FromNowOn` — permanent change, e.g. a raise: close the in-force row at `M−1` and insert a new one from `M` with `end_month = NULL`. **2 rows.**
3. `IncomeChangeScope.ThisMonth` — exceptional month: close the in-force row at `M−1`, insert a single-month row at `M` with the new amount, and **reopen** from `M+1` with the previous amount. **3 rows.**
4. Both branches go through a single helper, `applyIncomeChange(lineId, month, amount, scope)`. The scope is a **parameter of the operation, not a column** — the table stores only intervals.
5. Closed months keep the amount that was in force at the time. Navigating to a past month shows what was true then.

**Alternative flows**
- **Editing the label:** the scope question is **not** asked — it only makes sense for the amount. The rename applies to the in-force row and every future row with the same label (`UPDATE ... WHERE label = ? AND start_month >= ?`).
- **Editing a single-month line:** no scope question — there is no other month it could apply to — and the row is updated in place.
- **Amount change with no scope on a multi-month line:** rejected with `INCOME_LINE_NOT_IN_FORCE`'s sibling `INVALID_INCOME_CHANGE_SCOPE`. There is deliberately no default: assuming "from now on" would overwrite a one-off, assuming "this month" would quietly fail to apply a raise.
- **Editing a line the visible month no longer covers** (a stale panel after navigating months): rejected with `INCOME_LINE_NOT_IN_FORCE`.
- **`FromNowOn` inherits the original end:** a line already cancelled in December still ends in December after a raise in July — the new interval does not reopen it.

**Outcome**
- History is always truthful. `ThisMonth` produces three rows where the user conceptually sees one line — accepted cost of asking the question instead of forcing "from now on".

</details>

<details>
<summary>

### UC-INC-05 — Cancel an income line · DONE

</summary>

- **Status:** DONE
- **Actor:** Owner user
- **Trigger:** User cancels a line from the panel.

**Main flow**
1. Confirmation dialog.
2. The line is closed by setting `end_month = M−1`. History is **not** deleted: past months keep counting it.
3. A single-month line is deleted outright — there is no history to preserve.

**Alternative flows**
- **Cancelling in the line's own first month** (`M = start_month`), or from a month before it even starts: closing at `M−1` would leave `end_month < start_month`, which the schema forbids, and the line would never have applied to any month. It is deleted instead of closed.
- **Line already closed before `M`:** no-op, answered as a success. Cancelling twice is idempotent.

**Outcome**
- Cancelling stops the line going forward without falsifying any closed month. Cancelling every line makes the chip disappear, which is also how the feature is "turned off".

</details>

## Tareas técnicas

*Data model* (`server/schema.ts`):
- [x] Create table `income_lines`:
  - [x] `id INTEGER PRIMARY KEY AUTOINCREMENT`.
  - [x] `user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE`.
  - [x] `label TEXT NOT NULL`.
  - [x] `amount REAL NOT NULL CHECK (amount > 0)`.
  - [x] `start_month TEXT NOT NULL` (`'YYYY-MM'`), with a `GLOB` check — the whole interval logic relies on string comparison, so a non-uniform format would silently corrupt it.
  - [x] `end_month TEXT` (`NULL` = in force), checked for format **and** `>= start_month`.
  - [x] `created_at` / `updated_at TEXT NOT NULL DEFAULT (datetime('now'))`.
- [x] Index `idx_income_lines_user_month` on `(user_id, start_month)`.
- [x] Trigger `income_lines_updated_at` to refresh `updated_at` on row update.
- [x] No `scope` column and no `line_group_id` — both are deliberately absent (see Rules).
- [x] **No `runMigrations` entry needed**: `server/db.ts:16` runs `CREATE TABLE IF NOT EXISTS` on every boot; `runMigrations` is only for `ALTER` on tables that already exist in deployed databases.

*Shared types*:
- [x] `IncomeChangeScope` in the const-object + type pattern required by `CLAUDE.md` (`erasableSyntaxOnly` rules out native `enum`), members `ThisMonth: 'this-month'` and `FromNowOn: 'from-now-on'` → `shared/incomeChangeScope.ts`.
- [x] `IncomeLineRow` in `server/types.ts`.
- [x] `IncomeLine` and `MonthlyIncome` client types in `src/types/income.ts`.
- [x] Error codes in `shared/errorCodes.ts`: `MissingMonth`, `InvalidMonthFormat`, `IncomeLabelRequired`, `IncomeLineNotFound`, `InvalidIncomeChangeScope`. Amount validation reuses the existing `AmountMustBePositive`.
- [x] Both locale catalogs updated — `src/__tests__/lib/errorMessage.test.ts` enforces that every `ErrorCode` has es + en copy.

*Backend — resolver*:
- [x] The "in force" rule as a single SQL `WHERE`, in one place only → `server/helpers/listIncomeLinesForMonth.ts`.
- [x] The month's figure as a pure sum over those rows → `server/helpers/resolveMonthlyIncome.ts`. **Split into two files** (instead of the one originally planned) to respect the one-export-per-file rule; it also means a request fetches the rows once and serves both the figure and `lines[]` from them.
- [x] `applyIncomeChange(db, line, month, amount, scope)` in `server/helpers/applyIncomeChange.ts`, both branches in one transaction. Takes the already-fetched row so the route does not select twice.

*Backend — month keys* (`server/helpers/monthKeys.ts`):
- [x] `isValidMonthKey`, `previousMonthKey`, `nextMonthKey`. Grouped in one cohesive module like `recurringPeriods.ts`. `currentMonthKey` was dropped — every operation takes the month from the client, so nothing would call it.

*Backend — API*:
- [x] `GET /api/monthly-income?month=YYYY-MM` → `{ amount, spent, remaining, lines[] }`, pre-aggregated in one call (global no-N+1 rule). `spent` is `SUM(amount)` over `expenses` filtered by `user_id = req.userId` and the month, across all sheets, using the same `date LIKE ? || '%'` form as `server/routes/expenses.ts`. → `server/routes/monthlyIncome.ts`.
- [x] Amounts rounded to cents before subtracting: `REAL` arithmetic would otherwise leave a remaining like `-1e-10`, which renders as a negative figure in the wrong colour.
- [x] `POST /api/income-lines` → create (UC-INC-03). → `server/routes/incomeLines.ts`.
- [x] `PUT /api/income-lines/:id` → edit, body carries `month` and `scope` (UC-INC-04). Returns the lines in force for the month so the client refreshes from one response.
- [x] `DELETE /api/income-lines/:id?month=YYYY-MM` → cancel (UC-INC-05).
- [x] Every route asserts the line belongs to `req.userId`. No sheet permission checks anywhere — income is not sheet-scoped.
- [x] Mount behind `requireAuth` in `server/main.ts`.
